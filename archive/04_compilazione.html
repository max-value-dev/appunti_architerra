Compilatore, Assemblatore, Linker e Loader

Esempio concreto: la funzione scambia

Il compilatore GCC traduce C in assembly (con la flag -S). Lo stesso codice può essere scritto a mano in modo leggermente diverso ma equivalente. Nota la differenza — GCC usa alias simbolici (a0, a1), la versione del testo usa i numeri di registro (x10, x11):

Codice C sorgente
void scambia(size_t v[], size_t k) {
  size_t temp;
  temp   = v[k];
  v[k]   = v[k+1];
  v[k+1] = temp;
}
Output GCC (RV32I)
scambia:
  slli  a1, a1, 2
  add   a5, a0, a1
  lw    a4, 0(a5)
  addi  a1, a1, 4
  add   a0, a0, a1
  lw    a3, 0(a0)
  sw    a3, 0(a5)
  sw    a4, 0(a0)
  ret

L'assemblatore poi converte ogni istruzione mnemonica in 32 bit. Il GCC in questo esempio ha prodotto anche istruzioni compressed a 16 bit (estensione C di RISC-V): c.slli, c.lw, c.sw — sono versioni compatte di istruzioni comuni, riconoscibili dai byte hex più corti nel dump.

L'illusione delle Variabili: Nel codice C vedi nomi rassicuranti come temp o v[k]. Per la CPU, tutto questo non esiste. Il processore non ha la più pallida idea di cosa sia una "variabile". Vede solo sequenze di registri numerici (es. a4, a5) e indirizzi di memoria crudi (es. 0x1000). Il Compilatore è l'illusionista che mantiene l'associazione mentale tra il nome testuale che tu hai scritto e la scatola di silicio in cui ha deciso di confinarlo.

Traduzione per Java: JVM e JIT

Java Virtual Machine (JVM)

Il compilatore Java produce bytecode (non codice macchina nativo). La JVM lo interpreta a runtime — portabile su qualsiasi piattaforma che abbia una JVM.

Just In Time (JIT)

La JVM può invocare il compilatore JIT che compila i metodi hot in codice macchina nativo della CPU su cui gira. Risultato: velocità vicina al C, portabilità del bytecode.

RISC-V vs MIPS — formati incompatibili: entrambi sono ISA RISC a 32 bit, ma la codifica binaria è completamente diversa. RISC-V usa 7 bit per l'opcode, MIPS ne usa 6. Un binario RISC-V non può girare su una CPU MIPS e viceversa — l'ISA è il contratto tra software e hardware.

L'assemblatore a due passi

L'assemblatore traduce mnemonici in bit e risolve le etichette simboliche in indirizzi numerici. Deve farlo in due passi perché un'etichetta può essere usata prima di essere definita.

Il problema: forward reference

Nel codice assembly un salto può puntare a un'etichetta che appare più avanti nel file. Quando l'assemblatore incontra bgt a2,a3,.L20, non sa ancora dove si trova .L20 — quella etichetta verrà definita solo decine di istruzioni dopo. Questo si chiama forward reference. Il contrario (puntare a un'etichetta già vista) si chiama backward reference.

Passo 1 — Costruisce la Symbol Table

L'assemblatore scorre tutto il file senza tradurre. Per ogni etichetta trovata registra nella Symbol Table il nome e il valore dell'ILC (Instruction Location Counter) — la posizione relativa dell'istruzione nel programma.

Passo 2 — Traduce le istruzioni

Rescorre il file e traduce ogni istruzione in binario. Quando incontra un riferimento a un'etichetta consulta la Symbol Table costruita nel passo 1 — ora sa sempre dove si trova ogni etichetta, anche le forward reference.

Esempio: Symbol Table per is_sorted

is_sorted:
  ...        ← ILC = 0x420
  add   a4,a4,a0
.L18:      ← ILC = 0x432
  lw    a2,0(a5)
  lw    a3,4(a5)
  bgt   a2,a3,.L20  ← forward ref!
  addi  a5,a5,4
  bne   a5,a4,.L18  ← backward ref
  li    a0,1
  ret
  ...
.L20:      ← ILC = 0x462
  li    a0,0
  ret
Symbol Table (dopo passo 1)
SimboloValore ILC
is_sorted0x420
.L180x432
.L200x462
ILC = Instruction Location Counter — tiene traccia della posizione corrente durante la scansione. In RISC-V ogni istruzione è 4 byte, quindi l'ILC avanza di 4 ad ogni istruzione normale (2 per le compressed).

Passo 2: calcolo degli offset di salto

Nel passo 2 l'assemblatore sa che .L20 sta a 0x462 e che l'istruzione bgt a2,a3,.L20 sta a 0x43a. L'offset del salto è relativo al PC: 0x462 − 0x43a = 0x28 = 40 byte. Questo valore viene codificato nel campo immediato dell'istruzione B in linguaggio macchina.

Direttive, pseudoistruzioni e macro

Il linguaggio assembly offre strumenti aggiuntivi oltre alle istruzioni ISA: le direttive controllano l'assemblatore, le pseudoistruzioni sono alias comode, le macro sono template espandibili.

Assembly directives

Le direttive iniziano con un punto e danno istruzioni all'assemblatore su come organizzare il programma — non producono istruzioni macchina da sole:

Macro: template con parametri

Una macro è un template che viene espanso testualmente dall'assemblatore ogni volta che viene invocata — non è una funzione, non c'è jal/ret. Il codice viene duplicato inline ad ogni uso:

# Definizione della macro "swap"
.macro swap reg1, reg2, reg3
    add  \reg3, \reg2, zero   # reg3 = reg2
    add  \reg2, \reg1, zero   # reg2 = reg1
    add  \reg1, \reg3, zero   # reg1 = reg3
.endm

# Utilizzo
li   s1, 10
li   s2, 20
swap s1, s2, t0    # ← viene espanso nelle 3 add qui sotto

# Dopo espansione diventa:
# add t0, s2, zero
# add s2, s1, zero
# add s1, t0, zero

Il Linker

Un programma reale è diviso in più file sorgente compilati separatamente. Ogni file diventa un modulo oggetto con il suo spazio di indirizzi locale. Il Linker fonde tutto in un unico eseguibile con indirizzi definitivi.

Perché serve il linker?

Quando l'assemblatore traduce un file, molti indirizzi sono sconosciuti: la funzione printf è in un'altra libreria, la funzione B è in un altro file .c. L'assemblatore lascia questi indirizzi a zero e inserisce nel file oggetto le informazioni di rilocazione — una lista di "toppe" da applicare quando gli indirizzi saranno noti.

Struttura di un file oggetto ELF

Object file header

Descrive la dimensione e posizione di tutti gli altri segmenti nel file.

Text segment

Il codice in linguaggio macchina — le istruzioni da eseguire.

Static data segment (.data e .bss)

Contiene le variabili globali e statiche. È diviso in .data (variabili inizializzate, es. int x = 5;) e .bss (Block Started by Symbol: variabili non inizializzate, es. int y;, che vengono messe a zero dal sistema per risparmiare spazio nel binario).

Relocation info

Elenco di istruzioni e dati che dipendono da indirizzi assoluti ancora ignoti — da aggiornare dal linker.

Symbol table

Etichette esportate (definite qui, usabili dagli altri) e importate (definite altrove). Le voci importate hanno indirizzo "–" (unknown).

Debugging info

Mappa tra istruzioni macchina e righe del sorgente C — usata dal debugger (gdb, LLDB).

Cosa fa il linker: 4 operazioni

#OperazioneDettaglio
1Inventario moduliRaccoglie tutti i file .o e le librerie, registra le loro dimensioni (text + data)
2Assegna indirizzi baseDecide dove inizia ogni modulo nello spazio lineare: es. Procedura A inizia a 0x400000, B a 0x400100
3RilocazioneAggiunge a ogni riferimento di memoria la relocation constant = indirizzo di partenza del suo modulo
4Risolve simboli esterniAggiorna le istruzioni che chiamano funzioni di altri moduli con i loro indirizzi definitivi

Esempio: linking di procedura A e B

Procedura A chiama B con jal x1, 0 (indirizzo ignoto) e legge la variabile X. Procedura B chiama A e scrive Y. Dopo il linking:

# File oggetto A — indirizzi locali (relativi)
  0x00:  lw  x10, 0(x3)   # legge X — indirizzo ignoto
  0x04:  jal x1, 0        # chiama B — indirizzo ignoto

# File oggetto B — indirizzi locali (relativi)
  0x00:  sw  x11, 0(x3)   # scrive Y — indirizzo ignoto
  0x04:  jal x1, 0        # chiama A — indirizzo ignoto

# File eseguibile finale — indirizzi definitivi
# A inizia a 0x400000, B inizia a 0x400100
# X sta a 0x10000000,  Y sta a 0x10000020

  0x400000: lw  x10, 0(x3)      # x3=gp=0x10000000 → X
  0x400004: jal x1, +252       # 0x400100−0x400004=252
  0x400100: sw  x11, 32(x3)     # gp+32 = 0x10000020 → Y
  0x400104: jal x1, -260       # 0x400000−0x400104=-260
jal usa indirizzamento relativo al PC: l'offset nel binario è sempre la differenza tra l'indirizzo destinazione e l'indirizzo dell'istruzione jal stessa. Così il codice può essere spostato in memoria senza ricalcolare i salti interni al modulo.

Linking statico vs dinamico

Collegamento statico

Le librerie vengono incorporate nell'eseguibile al momento del linking. Vantaggio: eseguibile autosufficiente. Svantaggio: file grossi, aggiornare la libreria richiede ricompilare tutto.

Collegamento dinamico (DLL / .so)

Le librerie vengono caricate solo a runtime, al primo utilizzo (lazy binding). La prima chiamata passa per un dummy stub che invoca il loader dinamico; le chiamate successive vanno direttamente alla funzione — un salto solo.

Il Loader e il binding dinamico

Il Loader è un programma del sistema operativo che prende il file eseguibile dal disco e lo prepara per l'esecuzione in memoria centrale. È l'ultimo anello della catena prima che il codice giri davvero sulla CPU.

Le 6 operazioni del loader

Sequenza di caricamento
1

Legge l'intestazione del file ELF per determinare le dimensioni del segmento testo e dati.

2

Riserva uno spazio in RAM sufficiente a contenere codice, dati statici, heap e stack.

3

Copia il segmento testo (codice) dal disco alla RAM nello spazio riservato.

4

Copia nello stack i parametri passati al main (il famoso argc e argv).

5

Inizializza tutti i registri: imposta SP (stack pointer), GP (global pointer), PC (program counter), e azzera i registri temporanei.

6

Salta a una procedura di startup che copia i parametri dallo stack ai registri a0/a1 e poi invoca main.

Binding: quando si assegnano gli indirizzi?

Il binding è il momento in cui un nome simbolico (es. la variabile x o la funzione printf) viene associato a un indirizzo fisico di memoria. Esistono varie scelte:

Momento del bindingChi lo faVantaggi / Svantaggi
Al momento della scrittura del codiceProgrammatoreRigidissimo — indirizzi hardcoded nel sorgente
Al momento della compilazioneCompilatorePiù flessibile ma ancora statico
Al momento del linkingLinkerStatico — librerie incorporate nell'eseguibile
Al momento del caricamentoLoaderRilocazione al load time — programma spostabile
Al momento dell'esecuzioneOS + registro baseMassima flessibilità — DLL, shared libraries

Come funziona il linking dinamico lazy

La prima volta che il programma chiama printf, invece di saltare direttamente alla funzione salta a uno stub dummy che invoca il loader dinamico del sistema operativo. Il loader trova printf nella libreria libc.so, la mappa in memoria e sovrascrive l'indirizzo nello stub. Dalla seconda chiamata in poi il salto va direttamente a printf — nessun overhead aggiuntivo:

Prima chiamata a printf

1. jal ra, printf@plt → stub
2. Stub invoca il loader dinamico (OS)
3. Loader mappa printf in memoria
4. Aggiorna l'indirizzo nello stub
5. Salta a printf — esegue normalmente

Chiamate successive

1. jal ra, printf@plt → stub
2. Stub ora punta direttamente a printf
3. Salta a printf — un salto solo

Overhead = 1 salto indiretto extra, trascurabile.

PLT = Procedure Linkage Table: la tabella di stub usata per il lazy binding. Ogni funzione di libreria dinamica ha la sua voce nella PLT. Puoi vederla nel disassembly come printf@plt — è il "trampolino" verso la funzione reale.
